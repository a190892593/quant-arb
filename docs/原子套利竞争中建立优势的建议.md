# **Base + Arbitrum：如何在 DEX–DEX 原子套利竞争中建立优势并赚钱**

既然现在已经确定只做 **Base 和 Arbitrum One**，我建议把竞争策略重新收敛到这两条链，不再分散资源研究 BSC。

先说最重要的判断：

**我们不应该把目标定成“比所有机器人都快”，而应该定成“比竞争对手更早发现一部分机会、更准确判断机会是否真实可执行，并且只在值得竞争时出手”。**

DEX–DEX 原子套利确实吃速度，但速度只是竞争优势的一部分。真正决定长期能不能赚钱的，是：

1. 能不能发现其他机器人没发现、或没及时发现的机会。
2. 能不能准确算出指定本金下的真实净利润。
3. 能不能在机会消失前完成模拟、构造和提交交易。
4. 能不能在 Base 和 Arbitrum 各自的交易排序机制下有效进入区块。
5. 能不能控制竞价、失败交易和 Gas 成本，避免“抢到了机会却没赚到钱”。

我会把下面的方案设计成一个**以长期净利润为目标、以竞争效率为核心的套利系统**，而不是单纯追求扫描速度的机器人。

## **一、先看清楚：Base 和 Arbitrum 的竞争环境并不一样**

两条链不能简单共用一套“发交易抢速度”的策略。搜索逻辑可以统一，但数据接入、机会响应和交易提交必须链级适配。

**Base：200ms 原生区块竞争**

Base 已于 2026 年 11 月 5 日启用 Denim，改为每 200ms 产生一个正式区块，每秒 5 个区块。之前的 Flashblocks 机制已被替代，不应再把旧 Flashblocks WebSocket 或 pending 预确认状态当作当前实时数据基础。

**对我们的意义：** 需要快速订阅正式区块和交易状态，及时更新池状态、发现价格偏差。200ms 是区块节奏，不代表我们有 200ms 的完整反应时间，更不代表交易一定能进入下一个区块。

**Arbitrum：PGA 交易优先级竞争**

Arbitrum One 已使用 Priority Gas Auctions（PGA）取代 Timeboost。当前每个约 250ms 的区块有两个约 125ms 的优先级排序轮次，交易可以通过 Priority Fee 竞争排序位置。

Fast Feed 可以更早收到 Sequencer 已经排序并执行的交易信息，但它不是未排序的内存池，也不能让后来提交的交易插到已确定顺序的交易前面。

[image](https://www.google.com/s2/favicons?domain=https://developer.arbitrum.io\&sz=32)

**对我们的意义：** 除了快，还要根据竞争程度计算 Priority Fee，不能所有机会都用同样的竞价。

我的判断：

- **Base：** 重点做好高频状态更新、快速增量搜索、快速报价和准确模拟。
- **Arbitrum：** 在上述基础上，重点做好 PGA 竞价决策、Fast Feed 交易流观察和提交时机管理。
- **两条链共同的核心：** 链下先找到明确机会，链上只执行已经确定的路线，不让合约临时大范围搜索。

## **二、最重要的竞争策略：不要和所有机器人争同一批机会**

套利市场可以粗略分成三类机会。

| 机会类型             | 竞争情况             | 我们的策略               |
| ---------------- | ---------------- | ------------------- |
| 热门主流币、热门池的明显价差   | 通常竞争激烈           | 只在净利润足够覆盖竞价和失败成本时参与 |
| 多 DEX、多池、多跳的复杂路线 | 搜索空间更大，但不代表一定竞争低 | 重点投入路线发现和精确模拟       |
| 短暂流动性变化、池间状态不同步  | 需要快速发现和准确更新      | 建立实时监听和增量搜索能力       |

这里有一个非常重要的研究依据。

2026 年发表的《To Wait or To Probe: Arbitrage Competition on High-Throughput Blockchains》研究了 Base 在 2025 年 6 月至 2026 年 2 月的套利数据。研究将机器人区分为链下发现、固定路线提交，以及依赖链上探测的搜索方式。其样本中，概率式链上搜索约占成功套利活动的 23%，却贡献了约 95% 的垃圾交易，并消耗约 20% 的 Base Gas。

[image](https://www.google.com/s2/favicons?domain=https://drops.dagstuhl.de\&sz=32)

drops.dagstuhl.de+1



这项研究不能直接证明我们未来一定能赚多少钱，但它说明了一个值得重视的方向：

**不要把大量计算和 Gas 花在链上盲目探测。更合理的方式是链下充分搜索，确认机会后再提交固定路线。**

## **三、我建议建立六个竞争优势**

### **1. 建立比别人更全面的套利机会搜索范围**

不能只盯着几个主流 DEX，也不能只做简单的 USDC → WETH → USDC。

我们应该建立完整的 Token–Pool 图结构。

[Pathfinding Algorithms for DEX Aggregation and Smart Order Routing | by Jack Lodge | Deeplink Labs | Medium](https://images.openai.com/static-rsc-4/QxHIuSQmSvgahVqK8_26BYH053z5bIt87vMSjtSwJiNdAttYFe8bM88WieZCaXXQtNePGMvQsB5dMWmuEagk4GY-u3KqW6Qv_s9DWoQqd0UsxOJWjX_I-2qILBlukXSDm2kTRRLCayn0ERBZQjG5uZNS4x2XDSaq5WVgQvBuOl0?purpose=inline)

[medium.com](https://medium.com/deeplink-labs/pathfinding-algorithms-for-dex-aggregation-and-smart-order-routing-9e9feaf6b796?utm_source=chatgpt.com)

建议搜索范围：

| 路线类型      | 示例                         | 优先级 |
| --------- | -------------------------- | --- |
| 双池跨池套利    | USDC → WETH → USDC         | 高   |
| 三角套利      | USDC → WETH → DAI → USDC   | 高   |
| 跨 DEX 多跳  | USDC → WETH → TOKEN → USDC | 高   |
| 混合 AMM 套利 | V2 池 + V3 池 + 稳定币池         | 高   |
| 4–5 跳复杂闭环 | USDC → A → B → C → USDC    | 中高  |
| 稳定币池套利    | USDC → USDT → DAI → USDC   | 中高  |

DEX 协议接入方面，优先覆盖两条链上经过核实、具有真实交易量和流动性的主流池子，再逐步扩展。

路线搜索初期建议限制在 2–5 跳。不要因为跳数多就认为机会更好；每增加一跳，都要计算额外手续费、Gas、滑点和失败概率。

### **2. 实时增量搜索，而不是每次重新扫描全部池子**

这是我认为最值得投入开发资源的地方。

传统方式：

```
收到一个池子变化
    ↓
重新扫描所有池子
    ↓
重新枚举所有路线
    ↓
重新计算所有报价
```

更好的方式：

```
监听池子状态变化
    ↓
识别发生变化的 Pool
    ↓
查找所有经过该 Pool 的候选路线
    ↓
只更新相关路线
    ↓
快速重新报价
    ↓
筛选有利润的机会
```

例如：

假设 Base 有 20,000 个池子，某个 WETH/USDC 池发生变化。

系统不应该把 20,000 个池子全部重新计算，而应该直接找到所有包含该池的候选路线，只重新计算这些路线。

这会减少大量无效计算。

我建议系统维护：

- Token 索引
- Pool 索引
- Token → Pool 邻接表
- Pool → Route 反向索引
- Route 缓存
- 受影响路线队列
- 热门路线和冷门路线分级缓存

**真正的速度优势，往往来自少做无用功，而不是单纯使用更快的 CPU。**

### **3. 报价必须足够准确，不能只看表面价差**

很多机器人发现的所谓套利机会，实际上并不能赚钱。

例如：

**一个假设的套利机会**

初始资金

# **5,000 U**

表面价差利润

# **+35 U**

| 成本项目                         | 假设成本     |
| ---------------------------- | -------- |
| DEX 交易手续费                    | 8 U      |
| 滑点影响                         | 6 U      |
| Gas 成本                       | 3 U      |
| Priority Fee / Builder 等额外成本 | 5 U      |
| 其他执行成本                       | 1 U      |
| **最终净利润**                    | **12 U** |

以上仅为演示数字，不代表 Base 或 Arbitrum 的实时成本。

**最终净利润率**

# **0.24%**

我们的引擎应该同时计算：

- 250 U
- 500 U
- 1,000 U
- 2,500 U
- 5,000 U
- 7,500 U
- 10,000 U

每个资金档位的实际成交输出、滑点、手续费、Gas 和净利润。

尤其要做**最佳资金规模优化**：一条路线可能在 500 U 时有利润，到了 5,000 U 就因为流动性不足而亏损。

此外，还必须支持 V2、V3、稳定币 AMM 等不同定价机制的精确报价，不能用简单的现货价格差代替完整交易模拟。

### **4. 建立链下搜索 + REVM 模拟 + 链上固定路线执行**

这是我最推荐的系统架构。

**Base / Arbitrum 实时数据监听**

区块、交易、池子状态、流动性变化

**链下 Rust 套利搜索引擎**

增量搜索 · 2–5 跳路线 · 多资金档位报价

**REVM 本地 EVM 完整模拟**

真实合约调用 · 状态变化 · Gas · 最终净利润

**机会竞争评估**

竞争者 · 机会存活时间 · 竞价成本 · 风险门槛

**链上固定路线执行合约**

最低输出保护 · 最低净利润保护 · 原子交易

这套结构有三个关键优势：

- 搜索工作在链下完成，不需要每次在链上消耗大量 Gas。
- REVM 在本地执行完整 EVM 模拟，过滤掉很多虚假机会。
- 链上合约只执行指定路线，并检查最低输出和最低利润条件。

注意：原子交易不代表失败没有成本。交易回滚时，仍然可能损失 Gas。因此必须把失败成本纳入模型。

### **5. 建立竞争者分析系统，知道谁在抢我们的机会**

这点很重要，也是很多初级套利系统缺失的功能。

我们不仅要扫描套利机会，还要研究已经发生的套利交易。

建议记录：

| 研究指标             | 目的         |
| ---------------- | ---------- |
| 套利机器人地址          | 识别常见竞争者    |
| 交易发生的区块和时间       | 观察反应速度     |
| 涉及的 Pool 和 Token | 识别竞争路线     |
| 交易执行 Gas         | 研究成本结构     |
| Priority Fee     | 研究竞价习惯     |
| 成功和失败记录          | 估算执行效率     |
| 每次成功净利润          | 评估竞争者捕获的价值 |
| 交易提交与成交时序        | 估算机会存活时间   |

这里需要注意：一个地址不一定代表一个机器人，一个机器人也可能使用多个地址。我们的竞争者画像只能做概率识别，不能把地址数量直接当作机器人数量。

**我们要回答三个问题：**

1. 哪些路线竞争最激烈？
2. 哪些池子和路线长期存在盈利机会，但竞争者相对少？
3. 我们的机会是被别人先发现，还是发现后在交易排序阶段输掉？

这三个问题的答案，将决定我们究竟应该优化搜索引擎，还是优化交易发送层。

### **6. 建立动态竞价和放弃机制**

我不建议所有机会都用最高 Priority Fee 抢。

尤其 Arbitrum PGA 已经是明确的交易优先级竞争机制，竞价本身就是成本。

[image](https://www.google.com/s2/favicons?domain=https://blog.arbitrum.io\&sz=32)

Arbitrum, and the Ecosystem+1



建议建立三档竞争策略：

**低竞争机会**

积极参与

竞争者少、机会存活时间较长、净利润空间充足。

策略：使用较低成本的交易优先费，不必过度竞价。

**中等竞争机会**

动态竞价

存在其他机器人，但利润空间足以覆盖合理竞价。

策略：根据历史成功率、对手费用、机会净利润动态调整。

**高竞争机会**

严格筛选

热门路线、多机器人同时竞争、利润空间很薄。

策略：只在预期净利润明显高于竞争成本时参与，否则放弃。

竞价的核心判断应该是：

\\[ \text{参与价值} = P(\text{成功}) \times \text{成功净利润} - P(\text{失败}) \times \text{失败成本} - \text{额外竞价成本} \\]

只有参与价值大于我们的最低收益门槛，才应该发交易。

## **四、针对 Base 和 Arbitrum，分别怎么打？**

### **Base：重点打造高频状态更新和机会发现能力**

重点方向：发现速度 + 模拟准确度

Base 的 200ms 原生区块意味着我们应该围绕正式区块建立实时数据处理机制。

[image](https://www.google.com/s2/favicons?domain=https://www.base.org\&sz=32)

Base



我建议：

1. 使用支持 Base 实时区块订阅的高质量 WebSocket RPC。
2. 订阅 `newHeads`，及时获取新正式区块。
3. 对区块中的交易和日志进行增量解析。
4. 维护池子的实时状态，及时更新储备量、价格和流动性。
5. 每次状态变化只重新计算相关路线。
6. 使用 REVM 对候选交易进行本地完整模拟。
7. 根据实际利润和竞争情况决定是否提交。

**不要再按照旧 Flashblocks 方案设计 Base 的实时数据模块。** Denim 已经取代 Flashblocks，旧的 Flashblocks 订阅方式不再是当前主网方案。

[image](https://www.google.com/s2/favicons?domain=https://www.base.org\&sz=32)

Base+1



### **Arbitrum：重点打造 PGA 竞价和 Fast Feed 观察能力**

重点方向：交易排序 + 竞争成本

我建议：

1. 使用低延迟 RPC 和 WebSocket。
2. 评估是否接入付费 Fast Feed。
3. 使用 Fast Feed 观察已排序交易，研究竞争者行为和池子状态变化。
4. 对候选交易动态计算 `maxPriorityFeePerGas`。
5. 根据机会价值决定是否值得竞价。
6. 统一管理交易 nonce、提交状态、替换交易和失败成本。
7. 记录每次交易最终处于哪个 PGA 竞争环境，逐渐形成自己的竞价模型。

这里有个容易误解的地方：

Fast Feed 的价值是让我们更快观察已经排序的交易，而不是让我们提前看到所有待处理交易。已经进入排序队列并确定位置的交易，不能靠 Fast Feed 让我们的交易插队。

## **五、怎样找到竞争相对少、又能赚钱的机会？**

这是我认为最有可能建立差异化优势的方向。

我不建议只追求全市场扫描速度。我们可以建立一套**机会质量评分系统**。

每条套利路线至少记录：

| 评分维度   | 需要回答的问题                   |
| ------ | ------------------------- |
| 历史盈利能力 | 过去 30/90/180 天是否持续出现净利润？  |
| 机会出现频率 | 每天、每周能出现多少次？              |
| 竞争强度   | 有多少竞争者参与？                 |
| 机会存活时间 | 从首次出现到消失需要多久？             |
| 资金容量   | 5,000 U、10,000 U 是否仍然有利润？ |
| 模拟可信度  | 本地完整模拟是否成功？               |
| 执行成本   | Gas、竞价和失败成本是多少？           |
| 资产风险   | 是否有转账税、黑名单、暂停交易等风险？       |

最终我们不按照毛利润排名，而是按照：

**历史可实现净利润 × 机会频率 × 执行成功概率 − 全部成本和风险。**

这能避免一个常见错误：一条路线偶尔赚 100 U，但一个月只出现一次；另一条路线每次赚 8 U，每天出现 20 次。不能只看单次利润。

我建议系统进一步区分：

- `HIGH_COMPETITION`：高竞争路线。
- `MEDIUM_COMPETITION`：中等竞争路线。
- `LOW_COMPETITION`：低竞争路线。
- `INSUFFICIENT_DATA`：数据不足，无法判断。
- `VERIFIED`：完整模拟验证通过。

低竞争不等于一定赚钱，低流动性、长尾 Token 和异常池子仍然必须通过风险检查。


## **七、我建议先做 竞争力验证**

这一步非常重要。先用真实链上数据证明系统有没有竞争能力，不要一开始就投入实盘资金。

1. **第 1 ：实时数据和池子体系**
   - Base、Arbitrum 分别建立数据接入。
   - 建立 Pool Registry 和 Token Registry。
   - 测量区块和池子状态更新延迟。
   - 记录数据丢失、延迟和 RPC 异常。
2. **第 2 ：搜索引擎和完整模拟**
   - 支持 2–5 跳套利路线。
   - 实现增量搜索。
   - 实现不同本金档位的报价。
   - 接入 REVM 完整交易模拟。
   - 记录机会从发现到消失的时间。
3. **第 3 ：竞争者研究**
   - 分析历史成功套利交易。
   - 识别竞争者常用池子和路线。
   - 研究 Priority Fee 和 Gas 支出。
   - 估算热门机会和相对冷门机会的竞争差异。
4. **第 4 ：模拟竞争**
   - 模拟交易构造和提交。
   - 测试不同优先费方案。
   - 统计机会被别人先成交的比例。
   - 分析模拟执行成功率和预期净利润。

### **必须监控的指标**
